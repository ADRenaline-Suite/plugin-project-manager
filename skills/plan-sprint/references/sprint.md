# Sprint plan

Source: Scrum Guide, 2020. Sprint Planning produces the Sprint Goal, the selected items, and the plan to deliver them. The people who will do the work size it. This file does not size it. The file type is `sprint`.

## What it fixes

Why this period is valuable, which work is in it, and how that work will be delivered.

## How to do it

1. The sprint goal is one sentence a stakeholder can read. If an accepted outcome from `plugin-product` exists and the person ties the goal to it, cite that file. Do not write the outcome.
2. The timebox is the start and the end the person gave, or the length they gave. Do not invent dates.
3. Selected items are names the person gave, or files this plugin already wrote (a use case, a task, a backlog). Do not add an item.
4. The delivery plan points at a cross-repository task already written, or records the plan the person stated. Do not decompose the work into implementation steps and do not estimate a size.
5. An item with no file yet stays a name. Say the file is missing. Do not write that file in this turn unless they also asked for it.

## Template

Headings, in this order. Translate them.

## Sprint goal

required. Why this sprint is valuable.

## Timebox

required. The period. If the person did not give one, this heading is the gap.

## Selected items

required. Each item by name or by file.

## Delivery plan

required. The cross-repository task file, or the plan the person stated. No estimate.

## Done

- The four headings are present, in this order, in the language of the request.
- No item, date, outcome, or estimate was invented. A product outcome is a citation, not a paragraph copied from that plugin.
- The state is `accepted` only when the goal, the timebox, and at least one selected item came from the person. A missing timebox or an empty selection is a gap and the file is `proposed`.
